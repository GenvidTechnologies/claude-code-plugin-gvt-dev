# Release-Cycle Rules

Rules that keep main releasable, the version bump once per release cycle, and the CHANGELOG readable.

- **A feature chain that can't ship within one release cycle branches at the start, not at the end.** Landing the first link of a multi-issue feature on `main` makes `main` unreleasable for as long as the chain runs — and everything else merged meanwhile is held hostage with it. The cost is not the unfinished feature; it is that *finished, unrelated* work cannot ship, while the dogfood cache keeps lagging source (see the dogfooding caveat in [Dogfooding the Plugin](dogfooding-the-plugin.md)) and the open backlog keeps rotting against a moving `plugin/`. Judge this **when the first link lands**, not when the release is wanted: if the work is already scoped as a chain of issues, assume it will outlast the cycle. *(Worked example: `maintain-wiki` arrived via #143 as the first of a five-issue chain — #183 → #189, #190, #191, #192, plus #150 and #146. By 2026-08-04 that left 23 commits and 32 `[Unreleased]` CHANGELOG bullets unreleasable, of which only 2 bullets were the unfinished feature; the other 30 were finished refinements and fixes to already-released components. Unwinding it retroactively was judged too expensive — it was woven through five ADRs, `CONVENTIONS.md`, two other skills, and the dogfood `wiki/`+`raw/` trees — so the rule is worth applying up front, where it is free.)* Note the release surface is `plugin/` only (git-subdir), so a repo-root-only chain does not create this problem.

- **Versioning**: `plugin/.claude-plugin/plugin.json` carries a semver `version`. Bump it when shipping a meaningful change to skills/agents/hooks — but **once per release cycle, not once per change.** Compare `version` against the newest release tag (`git tag -l 'v*' | sort -V | tail -1`) and read the result **in both directions** — the rule has two cases, and only one of them is the one people remember:

  - **`version` is *ahead* of the newest tag** → this cycle's bump has already happened. Add your `[Unreleased]` CHANGELOG entry and **leave `version` alone** (except when the cycle gains a breaking change, below). Otherwise a second change in the same unreleased cycle double-bumps and desyncs the tag/marketplace `source.ref` contract.
  - **When `version` is ahead of the newest tag and the cycle now holds a breaking change** (a removed or renamed skill, agent or config key), set `version` to the next major, X+1.0.0, once. The major replaces the minor already taken this cycle and does not stack on it. A later breaking change in the same cycle leaves `version` alone. *(Worked example: #441 removed `maintain-wiki` and `wiki-librarian` while `plugin.json` read 4.50.0 against tag `v4.49.0`, so the branch set 5.0.0.)*
  - **`version` is *equal* to the newest tag** → this cycle's bump has **not** happened, and **your change owns it**: bump `version` alongside your `[Unreleased]` entry. Equal is the state a release leaves behind, so it is exactly what you find when you are the *first* change after one — and it is now common, because the release-before-dogfooding rule in [Dogfooding the Plugin](dogfooding-the-plugin.md) makes "release, then plan the next thing in the same session" the normal sequence rather than an edge case. *(Worked example: on 2026-08-07 a session cut `v4.6.0` mid-run and then planned #251 minutes later; `plugin.json` read 4.6.0 against tag `v4.6.0`, so that change correctly bumped to 4.7.0.)* The `[Unreleased]` entries' own "→ version bump at release" phrasing is the tell: the bump belongs to the *release*, which `release-plugin` owns — not to each change.
- **CHANGELOG entry shape**: each `[Unreleased]` bullet **closes with its version-bump verdict** — "New invocable skill → version bump at release.", "Behavioral skill/agent change → version bump at release.", "No consumer-facing behavior change → no version bump." The verdict classifies the change's release impact, so its wording stays the same when this change itself carried the cycle's bump under the *equal* case above. "→ version bump at release" next to a `plugin.json` already moved in the same branch is consistent, not a contradiction for a grader to flag. That clause is the entry's tail by convention, so when a later change **amends an existing entry** (the right move when the entry's subject hasn't shipped yet — a second `[Unreleased]` entry about the same unshipped surface is noise), the new sentence goes **before** the verdict, not after it. Appending past the tail reads as a second verdict and breaks the scan-the-last-clause habit the convention exists for.
- **The fix of an issue rewords every sentence that names its gap as open.** A doc or an `[Unreleased]` entry can describe a known gap and cite the issue that tracks it, for example "An ADR outside the bundle does not yet … (#1060)". When that issue is fixed, the sentence becomes false. Before the fix's pull request, run `git grep -n '#<N>'` and reword each hit that describes the gap as open. Leave a hit that records history, such as an observation from a retro. In #1060 the issue named the `CONVENTIONS.md` sentence, and the fix removed it; the `[Unreleased]` entry of #1046 had the same sentence, and only the code review found it.
- **A CHANGELOG entry that states another issue's state reads that state live.** An issue body records its cross-references as they were when the body was written. Before an entry says that another issue tracks, covers or will fix something, read that issue with `gh issue view <n> --repo <owner>/<repo> --json state,stateReason`. A closed issue is cited as the place where the work was done, not as open work. *(Worked example: the #930 entry first said that the `maintain-wiki` half was tracked in GenvidTechnologies/claude-code-plugin-gvt-wiki#24. The sentence came from the #930 body, triaged on 2026-11-13. That issue had closed as completed on 2026-11-16, and the retro of #930 corrected the entry.)*
- **A CHANGELOG sentence that says how behaviour changed is run on the old and the new code before the commit.** When an entry says that an input now gives one result and gave another before, run that input against the old code and against the new code, and compare both results with the sentence. For the old side, use a scratch copy of the file from the base commit (`git show <base>:<path>`), never the worktree. A sentence written from the design and not from a run can be false while every test passes, because no test reads the CHANGELOG. *(Worked example: the #951 entry first said that `**Blocked by nothing.**` at the end of a line now reads as no blocker. The run showed that it still read as a `prose` blocker: the full stop was followed by `**` and the end of the line, and the new sentence-end rule required a space. The rule was widened to accept the end of the line, and a test was added, before the pull request was opened.)*
- **Parallel side branches put their `[Unreleased]` entries at different points.** Two branches cut from the same base that both add an entry at the end of `[Unreleased]` change the same lines, so the second merge is likely to conflict. This is inferred from how git merges, not observed here. Put one branch's entry at the top of the section and the other's at the end. Before you open the second pull request, run `git merge-tree --write-tree --name-only <branch A> <branch B>`: exit 0 with only a tree id means the pair merges cleanly, and exit 1 lists the conflicting files. *(Worked example: the side pull requests for #1047 (entry at the end) and #1046 (entry at the top) were open at the same time against one integration branch. `merge-tree` printed only a tree id, and both merged with no conflict on 2026-11-22.)*
- **Parallel integration branches can take the same ADR number with no conflict.** Each branch names its record `NNNN-<own slug>.md`, so two records numbered 0105 are two different files, and git merges both. `commands.validate` runs `renumber-adrs.mjs --next`, which exits 1 and names both files when two records share a number. That check sees only the tree it runs on, so in the finish turn, after `origin/main` is merged in, run `commands.validate` again; on a duplicate, `git mv` this branch's record to the next free number, then change its heading and its index entry to match. `create-adr` §3 cannot do it, because the renumber script refuses a tree with a duplicate number. Text already posted on GitHub keeps the old number, so cite the record there by its title. *(Observed on 2026-11-23: the #906, #951 and #971 integration branches were open at the same time, and #906 took ADR 0105. No duplicate was found that day; the exit 1 on a duplicate was probed on a scratch directory.)*
- **The leak-guard check runs in `commands.validate`, not only in CI.** `.github/scripts/leak-guard.sh` is the one copy of its rules:
  - it blocks local paths and the username everywhere;
  - it blocks the `@genvidtech` npm scope in any tracked file except `*.md` and the plugin's own `package.json`/lockfile.

  Both `.github/workflows/leak-guard.yml` and `commands.validate` call it. Before this, it ran only in CI. #582's `create-adr-evals/grade.mjs` imported audit-core by its scoped package path, passed about 60 gated commits, and failed only on the chain PR (#616). From outside `plugin/`, where the `#audit-core` imports alias (ADR-0060) does not resolve, import the plugin's own re-export seam, `plugin/skills/audit-conventions/scripts/lib/audit-core-reexport.mjs` (ADR-0071), never `@genvidtech/...`.
